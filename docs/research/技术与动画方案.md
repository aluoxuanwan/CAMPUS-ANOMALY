# 校园主题 2D 动作游戏：技术与动画方案

> 检索日期：2026-10-07 | 目标：单机俯视动作 roguelite | 状态：架构建议，未安装引擎、建立游戏或执行性能基准

## 1. 引擎选型

推荐以 Godot 的稳定版本加 GDScript 制作首个战斗原型。它的场景、2D 节点、资源、动画与 UI 能覆盖当前范围，许可费用容易控制。正式生产应锁定经过验证的具体版本以及导出模板，避免长期依赖持续变化的 `stable` 文档地址。熟悉 Unity 的团队可以继续选 Unity，其既有经验和成熟组件可能节省更多时间。

| 引擎 | 已核实商业条件 | 本项目优势，属于工程判断 | 主要代价，属于工程判断 |
| --- | --- | --- | --- |
| Godot | MIT，商用可行，无引擎版税；保留许可与版权说明 [T01] | 原生 2D 工作流，个人原型成本低，场景与脚本易组合 | Steam、支付与第三方动画插件需要自己验证版本和平台支持 |
| Unity | Personal 门槛约 200,000 USD 收入与融资；Pro 2026 为每席年付 2,310 USD 或月付 210 USD [T02] | C#、成熟移动生态、商用组件和招聘资源较多 | 编辑器、包依赖和移动构建维护更重；超过门槛增加席位费 |
| GameMaker | 非商业免费；Professional 一次 99.99 USD，含桌面与 iOS 等出口 [T03] | 专注 2D，房间、精灵和快速动作原型直观 | GML 技术栈相对专门，复杂工具与平台组件需逐项核实 |
| Defold | 免费，无引擎版税；source available，自定义许可 [T04] | Lua、较轻运行时，2D 与移动性能预算友好 | 团队需熟悉消息与组件组织，复杂编辑器工具可能需补建 |
| Unreal Engine | 游戏常规版税 5%，首 1,000,000 USD 产品终身毛收入豁免，存在额外优惠与例外 [T05] | 团队已有 Unreal 经验或未来需要大量实时 3D 时有优势 | 本项目的 2D 内容与低配需求难以充分使用其大型 3D 工作流 |

Unity 已于 2024 年取消 Runtime Fee，并更新编辑器条款，不能继续用按安装收费的旧政策评估该项目。资格判断涉及组织收入与融资，外包提供服务还涉及客户口径。[Unity 官方条款更新](https://unity.com/blog/terms-update-runtime-fee-cancellation)

Defold 的授权允许商业游戏，但限制商业化引擎或编辑器本体；“源码可读”和通用开源许可证应准确区分。GameMaker 的主机发行需要另一档许可和平台审批，本次仅按 Windows/iOS 比较。所有购买价格为检索时公开页面值，税费、地区价格和后续更新可能改变成本。

决定引擎时用同一个小场景做对照：角色移动、两种攻击、30 敌人、200 投射物、遮挡排序、基本 UI 和一次导出。比较的重点是团队能否快速修问题、导出稳定性和内容接入速度。当前尚未做该对照，因此表中性能与便利性为选择判断。

## 2. Windows 与 iOS 的出口

Godot 可导出 Windows；其 iOS 官方流程要求从 macOS 加 Xcode 导出到 Xcode 工程，再处理签名和部署。官方文档仍将 C# 的 iOS 支持标为实验性并注明限制。针对个人跨平台原型，GDScript 可以避开这部分 .NET 移动风险，第三方插件仍须验证。[Godot iOS 导出](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_ios.html)

Unity 的典型 iOS 流程也会生成 Xcode 工程，再构建、签名和上传。GameMaker、Defold 和云构建可以有不同的自动化环节，iOS 工具链与签名仍须满足 Apple 要求。Defold 官方手册当前明确指出编辑器内 iOS 打包仅在 Mac 版可用。[Unity iOS 构建流程](https://docs.unity3d.com/6000.0/Documentation/Manual/iphone-BuildProcess.html)、[Defold iOS 手册](https://defold.com/manuals/ios/)

开发环境建议沿用现有 Windows 机器；2D 原型可用 16 GB 内存和 SSD，小团队 Unity 与美术同时运行可规划 32 GB。该建议属于工作负载预算，无法作为所有引擎的最低要求。新增电脑可暂用 4,000 至 8,000 元采购参数，实际价格需询价。iOS 阶段另外估算支持目标 Xcode 的 Mac、真实 iPhone、手柄与备份设备，暂留 5,000 至 12,000 元增量参数；旧设备兼容性要先查再采购。

电脑上成功启动编辑器，只能证明开发环境可用。正式流程还需导出一个包含目标插件的最小 iOS 工程，在真实手机运行，验证音频、触控、安全区、暂停恢复和签名。使用模拟器可以加快界面测试，不能替代发热、内存与实际触控验证。

## 3. 核心架构

把项目组织成输入、战斗规则、关卡、表现、数据与平台六个模块。输入模块把键鼠、手柄和触摸转换成移动向量、瞄准向量、攻击、冲刺和技能请求。战斗模块统一判定冷却、资源、攻击阶段与伤害。关卡模块管理房间、门、敌人波次与奖励。表现模块消费事件播放动画、特效、声音和 UI。平台模块隔离 Steam、iOS、成就、云存档与购买。

这种组织有两个实用收益。武器平衡变化只需改对应数据和规则，不必重写每种输入；替换角色画面时，已有碰撞与伤害规则仍可复用。表现与规则有明确接口，能够防止暂停、慢动作或动画结束回调意外改变冷却和战斗结果。

| 模块 | 主要职责 | 建议 Godot 对应工具 |
| --- | --- | --- |
| 玩家与移动 | 速度、加速、碰撞、受击位移 | CharacterBody2D，输入映射 |
| 攻击与投射物 | 伤害窗口、碰撞去重、寿命、阵营 | Area2D、形状查询、对象池 |
| 武器与能力数据 | 参数、标签、目标、触发、资源引用 | 自定义 Resource 或结构化配置 |
| 房间与场景 | 墙体、地面、遮挡、出生点、门 | Scene、TileMapLayer、TileSet |
| 动画与反馈 | 朝向、状态、事件、特效和声音 | AnimatedSprite2D、AnimationPlayer、AnimationTree |
| 局内与局外状态 | 随机种子、成长、解锁、版本迁移 | 独立 RunState 与 SaveService |

Godot Resource 适合可编辑的数据对象；同一资源引用可能被共享，因此运行时应把生命、冷却和临时叠加状态保存在独立实例中。不要修改共享定义来表示单个敌人受伤。[Godot Resources 文档](https://docs.godotengine.org/en/stable/tutorials/scripting/resources.html)

初版需要定义 WeaponDef、AbilityDef、ModifierDef、EnemyDef、RoomDef、EncounterDef、RewardDef 和 NarrativeEventDef。每项有稳定 ID、可显示名字、参数、标签和表现引用。表现文件路径变化不能改变存档中使用的 ID，帮助后续版本迁移。

## 4. 攻击判定与手感

一项攻击至少包含前摇、有效窗口和后摇。前摇告诉玩家和敌人动作将发生，有效窗口决定实际命中，后摇决定连续攻击与取消的边界。角色渲染方向不承担全部判定：攻击方向、武器方向和身体朝向各有用途，建议独立记录。

近战使用扇形、圆形或多段胶囊查询。每次攻击带 attack_id，对同一目标设置命中去重，避免在连续多个物理帧重复扣血。射击按投射物或直线查询实现，高速投射物应检查上一帧到本帧的扫掠路径，以防穿过薄墙和小敌人。墙、角色身体、攻击命中框和受伤框使用独立碰撞层。

冲刺定义开始、持续、结束以及独立无敌窗口。初始参数可以试验 0.12 至 0.20 秒无敌、0.5 至 0.9 秒冷却，但须在实际攻击模式中验证。这些数值是测试起点。无敌状态、攻击取消、被击硬直和推开墙体的优先级要写成规则表，并保证视觉提示与判定一致。

输入缓冲可先试验 80 至 120 ms，让玩家在上一动作即将完成时的攻击请求被接收；缓冲过长会让角色在玩家已松手后继续行动。命中停顿可先试验 20 至 60 ms，并根据武器、目标数和平台调整。每秒多次命中时应合并停顿请求，避免时间几乎停止。震屏与闪光强度允许玩家调低。

伤害建议按明确计算层结算：基础值加固定增加值，乘同组加成，再乘独立层倍率，随后处理防御、暴击、状态与最低伤害规则。实际公式由设计确定，UI 必须用同一规则描述生成预览。首轮先保留两至三个乘算层，便于平衡和解释。

技能触发用事件类型和来源标识管理，例如命中、暴击、击杀、冲刺结束、拾取和受伤。触发产生的新攻击需要标记是否允许再次触发。设置单次事件链的深度与次数上限；达到上限时记录原因，避免弹射、复制和击杀爆炸形成无限调用。

## 5. 敌人、寻路与房间生成

敌人可从有限状态机开始：出现、寻找位置、准备攻击、攻击、恢复、被控制和死亡。设计职责围绕追击、远射、盾卫、区域控制、召唤、冲刺六个家族。普通敌人优先用少量可见状态，Boss 使用专门阶段控制器。

每个物理帧更新移动和碰撞；感知与路径规划可以错峰执行，例如每 0.1 至 0.3 秒更新一次意图。追击敌人应在合适距离分散站位，减少所有敌人叠在一点的情况。远射敌人先检查视线与可攻击位置，再移动；寻路不能持续对每个敌人每帧重算。

程序生成分两层。先生成有起点、区域节点、精英、商店、恢复与 Boss 的房间图，检查连通和奖励规则；随后给节点填入人工布局模板、敌人组合和道具。房间内部通道、掩体和出生点仍然需要设计。随机种子和生成版本一起记录，方便复现某个不可完成的房间。

地面、碰撞、装饰、遮挡和危险层分别组织。Godot 的 TileMapLayer 适合按用途分层，当前类文档中旧 TileMap 已被弃用。[TileMapLayer 文档](https://docs.godotengine.org/en/stable/classes/class_tilemaplayer.html)

俯视场景按脚底位置进行 Y 排序；高墙可在主角进入后降低透明度或隐藏前景。装饰不应误导可走范围。实验桌、课桌和书架等可破坏物要有明确的受击与消失规则，避免碰撞留在原地或破坏后把出口封住。

## 6. 动画路线比较

| 路线 | 适合内容 | 优势 | 主要工作与代价 |
| --- | --- | --- | --- |
| 逐帧精灵 | 像素角色、夸张攻击、短特效 | 动作轮廓与像素可控，运行时播放简单 | 方向和动作成倍增加，换装和武器需要重画 |
| 2D 拆件骨骼 | 简洁手绘人物、NPC、可替换配件 | 复用骨骼、插值平滑、换装方便 | 拆层、绑权重、网格和遮挡；转身需要方向设计 |
| 3D 制作后预渲染为精灵 | 多方向角色、稳定动作与统一光照 | 建模和动画完成后可批量导出方向 | 前期 3D 技能成本，帧数图集体积，像素修整 |
| 实时 3D 加正交镜头 | 大量转向、动态灯光、可换装备 | 方向连续，动态光照与装备组合自然 | 模型、材质、实时性能与统一 2D 观感维护 |
| 混合方案 | 环境逐帧、人物骨骼、攻击逐帧特效 | 按资产选择适合的工具，减少重复 | 需要统一尺度、轮廓、光照和导入规范 |

Motion Twin 的官方 FAQ 确认 Dead Cells 大部分美术经历 3D 制作后转化为 2D 的流程，说明像素效果可以来自 3D 管线。能否节省本项目工时取决于已有技能、批量方向和修改次数，无法仅凭最终画面判断。[Motion Twin 官方 FAQ](https://motiontwin.com/faq)

首轮低分辨率像素原型建议逐帧主角和普通敌人，攻击特效独立播放。若选择简洁手绘，则可以先比较 Godot 自带 2D 骨骼与 Spine 的一个样张。已有 Blender 动画经验时，预渲染可以纳入对照。三条路线都需要在游戏内测试攻击判定、遮挡和高密度可读性。

## 7. 动画播放与事件

简单精灵可通过 AnimatedSprite2D 切换帧；需要曲线、方法事件和多属性动画时使用 AnimationPlayer；状态与混合控制使用 AnimationTree。官方文档说明，AnimationTree 控制 AnimationPlayer 内的动画，自己不存放动画。[Godot AnimationTree](https://docs.godotengine.org/en/stable/tutorials/animation/animation_tree.html)

主角基础状态建议为待机、移动、攻击、冲刺、受击和死亡，方向根据瞄准与移动规则确定。攻击状态与显示状态的优先级要固定，避免受击动画中仍能发射或冲刺结束后留在错误朝向。脚底基点、碰撞基点和武器持握点作为资产规范保存。

命中窗口由攻击数据与逻辑时间管理，动画事件可用来触发声音和特效。若编辑动画长度，攻击时间也必须同步审查，并记录变更。暂停、子弹时间和帧率变化应统一使用游戏时间，UI 与菜单可按实时更新。

像素动画可以用低帧率绘制并在 60 fps 游戏中播放，例如 8 至 12 fps 的动作资源。游戏帧率与动画帧率不同，减少绘制帧数通常降低生产量，但需要保留关键姿态、受击反应与移动稳定性。

## 8. 工具授权与制作费用

Spine 当前公开购买页显示 Essential 69 USD、Professional 379 USD；页面也显示被划掉的 99 和 449 USD，说明报价具有促销或调整背景。Essential 不含网格等高级功能；每位使用者需要对应许可，达到企业资格时采用 Enterprise。运行时集成需遵守 Spine Runtimes License，试用版不能作为最终授权依据。[Spine 官方购买与许可说明](https://esotericsoftware.com/spine-purchase)

Spine 的 Godot runtime 当前有 GDExtension 和自定义 C++ 引擎模块两种形式，官方文档指出功能与 C# 支持有差异。首选普通扩展时仍需确认引擎版本、Windows 与 iOS 二进制以及商业授权，避免到了移动导出才发现需要重建工具链。[Spine Godot runtime](https://esotericsoftware.com/spine-godot)

Aseprite 可作为像素逐帧编辑器，官方购买页当前价格需通过结账组件确认，本次未取得可靠静态金额，因此不写固定报价。Krita 可用于绘画，Blender 可用于建模、绑定和预渲染；免费软件仍要检查素材与插件各自许可。制作方法和工作量见配套素材清单。[Aseprite 官方购买](https://www.aseprite.org/buy/)、[Krita 授权说明](https://krita.org/en/about/license/)、[Blender 授权说明](https://www.blender.org/about/license/)

## 9. 包体、性能与配置

以下是工程预算区间，未运行相同项目测量，不能作为引擎性能排名。引擎版本、架构、渲染器、插件、调试符号和裁剪会显著改变空项目大小。

| 项目 | 暂定体积或资源预算 | 核验方法 |
| --- | --- | --- |
| Godot Windows 最小运行时及基本内容 | 粗留 50 至 120 MB | 用锁定版本、发行模板导出实测 |
| Unity Windows 最小运行时及基本内容 | 粗留 50 至 200 MB | 关闭开发构建，列出依赖并实测 |
| GameMaker Windows 最小运行时及基本内容 | 粗留 10 至 80 MB | 按实际 runtime 和出口实测 |
| Defold Windows 最小运行时及基本内容 | 粗留 3 至 30 MB | 检查发行构建和原生扩展 |
| 精简像素正式版整体 | 约 200 至 800 MB 的目标 | 以区域、图集、音频分别统计 |
| 较高分辨率手绘正式版整体 | 约 0.8 至 2.5 GB 的目标 | 同上，额外检查大图与帧数 |

引擎轻量性不会自动解决数千个高分辨率动画帧、完整配音或视频造成的体积。PNG 压缩大小也不能直接当作运行时纹理内存。RGBA8 的 2,048 方形纹理为 16 MiB，完整 mipmap 约再加三分之一；音乐应按时长与码率计算，见素材文档公式。

目标先定 1080p/60 fps、8 GB 系统内存、低档显卡或集显，最低型号由真实测试决定。单机离线的逻辑通常不需要长期服务器。iOS 更应限制透明特效覆盖、动态光源和同时播放声音，并在持续战斗后测试热降频。

优化顺序是测量最慢帧，再修最重部分。对象池用于频繁投射物、短特效和音效；空间查询减轻碰撞；寻路错峰；图集减少资源切换；按区域加载减少驻留；音乐流式播放。大量透明粒子覆盖整屏即使数量少也可能使移动 GPU 过载。

只有在性能采样证明 GDScript 成为主要瓶颈时，再把局部热点移至原生扩展。过早引入 ECS、原生模块或自研渲染器会增加维护与跨平台成本。当前规模先使用引擎普通场景组件，保留清晰接口。

## 10. 存档、平台与工程维护

存档分为永久进度与当前局状态。永久进度保存解锁、货币、设置、叙事标签和版本；局状态保存角色参数、装备、能力、随机种子、当前房间和必要计时。首版可以在房间完成后保存，移动端进入后台也需要可恢复的最近状态。

采用临时文件写入后替换正式文件，保留一个最近可用备份，并为版本升级写迁移规则。跨平台云存档、退款和内购恢复涉及平台接口，不能用普通文件复制覆盖全部需求。公开版本保留版本号、提交标识和对应调试符号，便于定位崩溃。

开发中使用 Git 与大文件管理或其他可靠版本方案，自动备份源素材。数据编辑可以先从表格或 Resource 开始；当 36 房间和大量技能需要反复修改，再建设房间验证器、技能预览器和叙事条件跳转工具。工具投入需要以节省的重复人时判断。

针对正式游戏，需要验证攻击去重、触发上限、随机图可达、存档迁移和暂停恢复等真实风险。自动模拟数值能发现极端组合，无法替代玩家对手感、可读性和节奏的判断。本研究没有创建测试代码或声称这些验证已经通过。
